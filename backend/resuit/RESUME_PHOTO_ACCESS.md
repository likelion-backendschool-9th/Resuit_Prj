# 이력서 사진 조회 권한

새 이력서 사진은 `resumePhotos/{userId}/{uuid}.{extension}`에 저장하고 `/media/resumePhotos/...` URL을 반환한다. 기존 `/media/image/...` 사진은 저장하거나 복제할 때 별도 파일로 복사한다. 제출용 `resumeSnapshots` 저장과 조회 권한 검사는 유지한다.

`/media/image/**`의 정적 리소스 매핑을 제거하고, 새 주소와 기존 주소 모두 백엔드 컨트롤러에서 조회 권한을 검사한다. 기존 사진의 DB 주소를 일괄 변경하거나 파일을 이동하는 마이그레이션은 필요하지 않다.

- 소유자는 본인 사진을 조회할 수 있다.
- 다른 로그인 회원은 공개 공통 이력서 또는 취소되지 않은 피드백 요청의 사진을 조회할 수 있다. 기존 이력서 미리보기 정책과 같다.
- 유료 피드백 요청자와 지정 멘토는 해당 요청에 연결된 이력서 사진을 조회할 수 있다.
- 비로그인 사용자는 이력서 사진을 조회할 수 없다. 새 주소는 401, 기존 이미지 주소의 권한 없는 조회는 존재 여부를 감추기 위해 404를 반환한다.
- 기존 이미지 파일은 이력서 참조가 없고 파일 업로더 본인의 공개 게시글 또는 프로필 이미지로 명시적으로 사용 중일 때만 익명 조회를 허용한다. 이력서 참조가 있으면 이력서 권한이 우선한다.
- 이력서를 삭제하거나 사진을 교체한 후 남은 파일은 업로더만 조회할 수 있다. 파일이 남았다고 공개 리소스로 취급하지 않는다.
- 파일명·소유자 경로를 제한하고 심볼릭 링크를 거부한다. 권한 확인 후 파일을 제공하며 `Cache-Control: no-store`, `Vary: Cookie`, `X-Content-Type-Options: nosniff`를 반환한다.

## 운영 반영

운영의 `/media/` 요청은 백엔드로 전달되어야 한다. 저장소의 nginx 설정과 Next.js rewrite는 이 조건을 충족한다. 별도 CDN 또는 외부 정적 파일 서버가 `image/`를 직접 공개한다면 그 경로를 제거해야 한다. 기존에 캐시된 이력서 사진은 프록시/CDN 캐시도 삭제해야 한다. 이미 다운로드한 사진을 회수하는 기능은 아니다.

공개 게시글 이미지와 같은 파일을 이력서 사진으로 사용한 기존 데이터에서는 이력서 권한이 우선하므로 공개 게시글 이미지도 익명 조회가 제한될 수 있다. 소유자가 해당 이력서를 다시 저장하면 사진이 별도 private 경로로 복사되어 분리된다.

## 확인한 시나리오

격리된 H2 및 PostgreSQL 검증 DB에서 실제 세션 인증과 HTTP 요청으로 확인했다. 운영 DB와 기존 로컬 DB의 이력서는 변경하지 않았다.

- 소유자 조회, 비로그인 차단, 타인 비공개 사진 조회 차단
- 공개 전환 후 허용, 비공개 전환 후 다시 차단
- 타인 사진을 본인 이력서에 저장하는 요청 차단, 본인 사진 재저장
- 기존 이미지 URL의 동일한 권한 검사
- 유료 피드백 지정 멘토와 활성 피드백 요청에 대한 허용
- 요청 취소 및 이력서 삭제 이후 타인 조회 차단
- 공개 게시글·프로필 이미지 익명 조회 유지
- 타인이 프로필에 사진 URL을 붙여 공개 판정을 받으려는 우회 차단
- 공개 이미지에 심볼릭 링크를 연결한 우회 차단

## 코드 배치와 DI

컨트롤러는 `service/ResumePhotoAccessService` 인터페이스를 생성자로 주입받는다. 실제 권한 검사와 파일 조회는 `service/impl/ResumePhotoAccessServiceImpl`의 `@Service` 구현체에서 수행한다. 조회 조건은 `dto/ResumePhotoQuery`, 허용된 바이너리 파일과 MIME 타입은 `dto/ResumePhotoResource`에 둔다. 저장소 조회는 기존 `repository`를 사용하고 설정은 기존 `config`에 둔다.
