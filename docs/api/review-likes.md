# 리뷰 좋아요 등록·취소

- POST `/api/v1/reviews/{id}/likes`: 좋아요 등록
- DELETE `/api/v1/reviews/{id}/likes`: 본인의 좋아요 취소
- 성공 응답: `{"reviewId":1,"liked":true}` (취소 시 false)
- 중복 등록과 반복 취소 모두 200으로 현재 요청 상태를 반환한다.
- 인증되지 않았거나 해당 사용자명이 DB에 없으면 401, 양수가 아닌 ID는 400, 없는 리뷰는 404를 반환한다.

## 사용자 식별

Servlet의 인증된 Principal 이름을 `users.username`으로 조회한다. 현재 프로젝트에는 인증 제공자가 없으므로 실제 로그인 통합 전에는 401을 반환한다. 사용자 ID 헤더나 요청 본문으로 인증을 대체하지 않는다. 인증 담당자가 Principal 이름을 UUID 등으로 정하면 이 경계를 함께 변경해야 한다.

## DB 기준

현재 엔티티와 작업 폴더의 `ai짬떄리기.sql` 구조를 기준으로 한다. `docs/erdcloud/resuit_erd_import.sql`은 이번 작업에 사용하지 않는다.

`feedback_comment_likes`의 `(comment_id, user_id)` 복합 PK와 두 FK가 실제 PostgreSQL에 필요하다. 등록은 `INSERT ... ON CONFLICT DO NOTHING`으로 동시 중복 등록을 처리하며 생성 시각을 직접 저장한다. 취소는 댓글 ID와 로그인한 사용자 ID를 모두 조건으로 삭제한다. 실제 DB에는 아직 변경 SQL을 실행하지 않았다.

베스트 리뷰와 명예의 전당 조회는 구현되어 있다. 채택 API는 요청당 한 개 정책으로 구현되어 있다.

## 베스트 리뷰 조회와 프론트 연동

`GET /api/v1/reviews/best?period=WEEKLY` (또는 `MONTHLY`)

- 기간은 대소문자를 구분하지 않으며 생략하면 WEEKLY다. 다른 값은 400이다.
- 해당 기간 유형의 가장 최근 `period_start` 선정 결과를 `rank_no`, 선정 ID 순으로 반환한다.
- `best_reviews.period`는 weekly/monthly를 사용한다. 기존 대문자 값도 조회할 수 있다.
- 선정 행이 없으면 `reviews: []`를 반환한다. DB 오류는 빈 목록으로 숨기지 않는다.
- 좋아요 수는 현재 DB에서 집계한다. 기존 선정 순위는 좋아요 변경으로 다시 계산하지 않는다.
- 로그인 전에도 목록을 조회할 수 있다. 로그인 전 liked는 false다.

```json
{
  "period": "WEEKLY",
  "reviews": [{
    "reviewId": 1,
    "username": "reviewer",
    "nickname": "리뷰어",
    "content": "프로젝트에서 맡은 역할을 구체적으로 적어 보세요.",
    "section": "project",
    "adopted": false,
    "periodStart": "2026-11-02",
    "rank": 1,
    "likeCount": 3,
    "liked": false
  }]
}
```

웹 진입 경로는 `/reviews/best`이며 왼쪽 이력서 하위 메뉴에서도 이동한다. 주간·월간 탭, 로딩, 빈 목록, 실패·재시도, 좋아요 결과와 인증 오류를 표시한다. API 서비스 함수는 `frontend/src/services/reviews.js`에 분리했다. mock 계정의 로그인 상태를 서버 인증으로 취급하지 않는다.

### 팀 연동 항목

| 담당 경계 | 합의·구현할 내용 |
| --- | --- |
| 인증 | 서버 Principal 이름을 users.username으로 전달하고 동일 출처 쿠키 인증을 연결. 다른 식별자 계약을 쓰면 ReviewService 사용자 조회 변경 |
| 피드백 | feedback_comments.comment_id / feedback_id / user_id와 users.id 관계 유지. 실제 저장된 댓글만 좋아요·선정 가능. 프론트 mock 댓글 ID와 실제 DB ID는 호환되지 않음 |
| 베스트 선정 | 선정 기준, 주간·월간 경계와 시간대, 인원, 동점 처리, 실행 주체를 합의한 뒤 best_reviews 저장 로직 구현. 현재는 저장된 선정 결과만 조회 |
| 채택 | 요청자 본인 확인과 채택 가능 개수 정책이 필요. 채택 API는 요청자만 실행할 수 있으며 요청당 한 개로 제한 |
| DB | feedback_comment_likes 복합 PK·FK 및 현재 엔티티와 실제 스키마 일치 확인. 참조 SQL 전체 자동 실행·DDL 자동 변경 없음 |

### 실행 경로

- 로컬: 백엔드 8080, frontend에서 `npm run dev` 후 `http://localhost:5173/reviews/best`.
- Next.js의 `/api/*` 프록시 대상 기본값은 `http://localhost:8080`. 다른 주소는 프론트 실행/빌드 시 BACKEND_URL로 지정.
- Docker 개발 환경은 compose.override.yml에서 BACKEND_URL=http://backend:8080을 지정한다. 설정 변경 시 frontend 재시작 필요.
- 기존 Nginx 경로에서는 `/api/`를 backend:8080으로 전달한다.
- 백엔드 실행에는 기존 POSTGRES_HOST/PORT/DB/USER/PASSWORD 환경 설정이 필요하다. 검증 환경에는 Resuit DB 설정이 없어서 실제 API·DB 왕복은 아직 확인하지 못했다.

### 검증

- backend: `bash gradlew compileJava --offline` 성공.
- frontend: `npm run build` 성공, `/reviews/best` 라우트 생성 확인.
- 실제 브라우저 조작, DB 데이터 조회·좋아요 저장, 로그인 세션 전달, 운영 배포는 미검증.

## 개인 DB 실연동 확인 (2026-11-04)

앞의 미검증 기록 중 다음 항목을 실제 확인했다.

- 개인 PostgreSQL: localhost:5433/resuit, resuit_prj-db-1 컨테이너 healthy.
- 기존의 빈 개인 DB에 Hibernate ddl-auto=update를 이번 초기화 실행에만 적용하여 엔티티 기준 테이블 28개, FK 52개 생성.
- 제외한 ERD SQL은 실행하지 않았다. 다른 프로젝트의 DB·컨테이너는 변경하지 않았다.
- 로컬 백엔드 8081: 빈 목록 200, 잘못된 period 400, 비인증 좋아요 401 확인.
- database/local/review-demo.sql로 명확히 샘플로 표시된 리뷰 추가 후 WEEKLY/MONTHLY 목록과 DTO 매핑 모두 200 확인.
- 샘플은 로컬 화면 확인용이며 운영·공용 DB에 실행하지 않는다. 샘플 ID는 900001/900002를 예약한다. 자동 선정 기능·로그인 계정이 아니다.
- 인증된 사용자의 HTTP 좋아요 요청은 인증 연동 전이므로 여전히 미검증이다.

### 현재 개인 환경 재실행

프로젝트 루트의 .env를 사용한다. 비밀번호가 포함된 파일은 Git에서 제외된다.

```bash

cd backend/resuit
SPRING_JPA_HIBERNATE_DDL_AUTO=validate ./gradlew bootRun --args='--server.port=8081'
```


공용 DB에는 ddl-auto=update를 적용하지 않는다. 다음 스키마 변경은 변경 SQL을 준비하고 실제 DB와 대조한다. 개인 DB 볼륨을 삭제하면 샘플과 테이블도 사라지므로 임의로 down -v를 실행하지 않는다.


## 명예의 전당 (WBS 7.6)

- API: `GET /api/v1/reviews/hall-of-fame?page=0&size=20`
- 웹: `/reviews/hall-of-fame` (왼쪽 이력서 메뉴 및 베스트 리뷰 화면에서 이동)
- page: 0~100000, size: 1~50. 범위 위반·잘못된 숫자는 400.
- 정렬: 선정 기간 시작일 내림차순 → 기간 유형 → 순위 → 선정 ID. 동일 조건에서도 선정 ID로 순서를 고정한다.
- 응답: reviews, page, size, totalElements, hasNext.
- reviews 각 항목: selectionId, period(WEEKLY/MONTHLY), review(베스트 리뷰 응답과 동일한 공통 DTO).
- 같은 댓글이 여러 기간에 선정되면 선정별로 표시한다. React key는 댓글 ID 대신 selectionId를 사용한다.
- 좋아요는 댓글 단위이므로 같은 댓글의 여러 선정 카드에 함께 반영한다.
- 로딩·빈 결과·조회 실패와 재시도, 이전·다음 페이지를 제공한다.
- 모든 과거 기록을 반환하며 현재 댓글 내용과 좋아요 수를 보여준다. 선정 당시 본문을 복제 보관하는 구조는 현재 ERD에 없다.

검증: 개인 PostgreSQL의 샘플 선정 2건으로 size=1의 첫/다음 페이지, 전체 개수, hasNext, 범위를 벗어난 빈 페이지 확인. 음수 page·초과 page·초과 size·비숫자 page의 400 확인. 프론트 경유 API 및 페이지 HTTP 200 확인. 백엔드 컴파일과 프론트 빌드 성공. 실제 브라우저 클릭 및 인증 후 좋아요 저장은 여전히 미검증이다.

### 구분용 로컬 리뷰 샘플 갱신

현재 표시 데이터는 프론트 mock.js가 아니라 개인 PostgreSQL에 저장한 샘플이다. 실제 사용자가 작성한 운영 데이터는 아니다. 주간 2건(프론트엔드 성능·백엔드 쿼리), 월간 2건(경력 소개·UX 개선)으로 작성자·분야·본문을 구분했다. 로컬 샘플 예약 ID 범위는 900001~900004이며 `database/local/review-demo.sql` 재실행으로 같은 샘플을 갱신할 수 있다. 이번 변경 후 프론트 API 경유로 주간·월간 각각 2건과 명예의 전당 서로 다른 본문 4건을 확인했다.

### 과거 선정 기록 확장

개인 개발 DB의 화면 확인용 가상 데이터를 18명, 리뷰·선정 기록 54건으로 확장했다. 12주 × 3건, 6개월 × 3건이며 명예의 전당 기본 20개 기준 3페이지다. 사용자명·닉네임·본문에서 화면용 샘플 표기를 제거하고 자연스러운 한국어 피드백으로 구성했다. 좋아요와 일부 채택 상태도 DB에 저장했다. 실제 사용자가 작성한 운영 데이터는 아니며 프론트 mock 데이터로 대체하지 않는다.

예약 ID는 900001~900054, 사용자 UUID는 같은 끝자리 범위를 사용한다. `database/local/review-demo.sql`은 이 개발용 레코드를 갱신하므로 개인 DB에서만 실행한다. 날짜는 실행일의 주·월 시작일을 기준으로 생성되며 각 기간 선정 3건씩을 만든다. 재실행 시 기존 좋아요는 삭제하지 않는다.

최신 주간·월간 각 3건, 화면 표기 변경, 명예의 전당 20/20/14건 및 중복 없는 선정 ID 54개를 실제 프론트 API로 검증했다. 운영 기능의 자동 선정이나 실제 활동 실적을 검증한 것은 아니다.

피드백 본문 다양화: 기존 18개 주제의 반복 구성을 제거하고 54개 본문을 개별 작성했다. 좌석 동시 예약, 메모리 누수, 결제 정밀도, 캐시 무효화, 접근성, 이전 직무 경험, 채팅 재접속, 대용량 파일 처리 등 서로 다른 상황과 개선 제안을 담았다. 개인 DB에 반영 후 프론트 API로 본문 54개 및 도입부 54개가 모두 다름을 확인했다.


## 리뷰 채택 (WBS 7.4)

사용자 결정: 피드백 요청 하나당 채택 리뷰는 한 개다. 채택 취소·다른 리뷰로 변경은 이번 API 범위에 없다.

- `POST /api/v1/reviews/{reviewId}/accept`, 요청 본문 없음.
- 인증된 Principal 이름으로 users.username 조회. 사용자 ID를 클라이언트 입력으로 받지 않는다.
- 요청자 본인만 채택 가능. 타인 403, 비로그인 401, 없는 리뷰 404, 잘못된 양수 ID 400.
- 취소한 피드백 요청에서는 409 REQUEST_CLOSED.
- 다른 리뷰가 이미 채택됐으면 409 REVIEW_ALREADY_ACCEPTED.
- 같은 리뷰를 다시 채택하면 기존 채택 시각을 유지하며 200을 반환한다.
- 성공 DTO: reviewId, adopted, adoptedAt. PostgreSQL 정밀도에 맞춰 시각은 마이크로초 단위로 저장한다.
- 요청 행을 PESSIMISTIC_WRITE로 잠근 뒤 기존 채택을 조회하고 변경한다. 같은 요청의 동시 채택은 직렬화된다.
- DB에서도 `database/migrations/001_one_accepted_review.sql`의 부분 유니크 인덱스로 feedback_id별 is_adopted=true 행을 한 개로 제한한다. 개인 DB에는 적용 완료.
- 기존 DB에 중복 채택이 있으면 인덱스 생성이 실패한다. 공용 DB 데이터를 자동 수정하지 말고 기존 채택 처리 기준부터 협의한다. Hibernate update/validate만으로 이 인덱스는 생성되지 않는다.
- 프론트 목록 응답의 canAccept는 요청자 본인이고 요청이 유효하며 아직 채택 리뷰가 없을 때만 true다. 버튼 노출과 별개로 서버가 다시 권한·상태를 확인한다.
- 베스트 리뷰와 명예의 전당에서 채택 후 목록을 다시 조회해 같은 요청의 다른 리뷰 버튼도 갱신한다.
- 로그인 연동 전에는 채택 버튼이 보이지 않으며 API 호출은 401이다. 화면 확인을 위해 인증 우회를 추가하지 않았다.

개인 DB의 가상 데이터도 요청당 한 개 채택으로 재구성했다. 로컬 seed 재실행은 예약 리뷰 범위의 채택을 재설정하므로, 수동으로 테스트한 채택을 보존해야 할 때는 실행하지 않는다.

채택 검증 결과: 추적되지 않는 임시 Java 검증 프로그램에서 실제 Spring 서비스·트랜잭션과 개인 PostgreSQL을 사용해 비인증, 타인, 없는 리뷰, 정상 저장, 같은 리뷰 반복 요청의 시각 유지, 다른 리뷰 채택 충돌, 취소 요청 거부, 두 스레드 동시 요청 중 정확히 한 개 저장을 확인했다. 임시 요청·댓글은 검증 후 삭제했다. 프론트 경유 비인증 POST의 401과 익명 목록 canAccept=false, DB 중복 채택 그룹 0개도 확인했다. 백엔드 컴파일과 프론트 빌드 성공. 실제 로그인된 브라우저에서 버튼을 눌러 저장하는 검증은 인증 담당자 연동 후 필요하다.

추가 DB 검증: 실제 서비스 호출로 좋아요 등록·중복 등록·반복 취소·다른 사용자 좋아요 보존을 확인했다. 같은 사용자·리뷰에 8개의 동시 등록 요청을 보내도 복합키 한 건만 유지됨을 확인했다. 임시 댓글·요청과 좋아요는 검증 후 정리했다. 이는 로그인된 HTTP 브라우저 흐름과는 별개의 서비스·DB 검증이다.

## 자동 선정 실행·운영

- BestReviewSelectionScheduler는 한국 시간 매일 00:05와 서버 시작 완료 시점에 직전 완료 주간·월간을 점검한다. 매주 월요일에는 지난 주를, 매월 1일에는 지난달을 처음 확정한다.
- 완료된 기간의 상위 3개를 best_reviews에 저장한다. 좋아요 수 → 기간 종료 전에 채택된 리뷰 → 작성 시각 → 댓글 ID 순이다. 마지막 댓글 ID는 작성 시각까지 동일할 때 결과를 일정하게 만드는 보조 정렬이다.
- 좋아요는 현재 남아 있는 행 중 기간 종료 이전에 생성된 것을 집계한다. 종료 이후 좋아요와 채택은 반영하지 않는다. 좋아요 취소 이력을 보관하는 테이블이 없어 장기 장애 후 과거 집계를 재구성할 때 취소된 좋아요의 당시 상태까지 복구하지는 못한다.
- database/migrations/003_best_review_selection.sql은 개인 DB에 적용했다. best_review_selections 테이블의 기간별 PK로 실행을 선점하고, 결과 저장과 같은 트랜잭션에서 확정한다. 실패하면 선점도 롤백되어 재시도할 수 있다.
- 후보가 0개여도 완료 기록을 남긴다. 후보가 부족하면 있는 수만큼 저장한다. 완료된 기간은 실행을 반복하거나 좋아요·채택이 바뀌어도 다시 선정하지 않는다.
- 기존 best_reviews 결과가 있는 기간은 덮어쓰지 않고 완료로 기록한다. 과거 결과는 명예의 전당에 유지한다.
- 기간별 순위·댓글 중복도 부분 키가 아닌 유니크 인덱스로 방지한다. 기존 공용 DB에 중복 선정이 있으면 migration은 실패하며 데이터를 임의 삭제하지 않는다.
- 스케줄러 비활성화: RESUIT_REVIEWS_SELECTION_ENABLED=false. 기본은 활성화다. 여러 인스턴스에서 실행돼도 DB 선점으로 한 번만 처리된다.
- 서버 시작 시 직전 완료 주간·월간만 확인한다. 여러 기간의 장기 누락은 운영자가 BestReviewSelectionService.select(period, start)로 완료 기간을 지정해 복구해야 한다. 공개 실행 API는 추가하지 않았다.
- created_at/ adopted_at은 기존 엔티티의 시간대 없는 LocalDateTime이다. 한국 시간으로 저장된다는 전제이며 Docker backend에 TZ=Asia/Seoul을 지정했다. 로컬 JVM도 한국 시간으로 실행하고, 다른 시간대로 저장된 공용 DB의 기존 값은 적용 전에 확인해야 한다.
- 개인 DB 가상 기록은 자동 생성 결과가 아니다. 운영 DB에 seed를 적용하지 않는다.

자동 선정 검증: 실제 Spring 서비스·개인 PostgreSQL에서 상위 3개, 좋아요 수 정렬, 동점 시 채택·작성 시각 우선, 시작 포함·끝 제외, 주간·월간, 후보 2개·0개, 확정 순위 유지, 4개 동시 실행에서 한 번만 처리, 미래 기간 거부를 확인했다. 검증용 데이터는 정리했다. 실행 중인 서버에서도 2026-10-26 주간·2026-10-01 월간 완료 기록이 생성됐고 기존 선정 결과는 보존됐다. 백엔드 컴파일과 기존 프론트 베스트 리뷰 API 200을 확인했다. 실제 자정 스케줄 시각까지 기다리는 검증은 수행하지 않았다.
